Event-Driven Architecture

الأسبوع 63: بناء أنظمة تتفاعل مع الأحداث بدلاً من الأوامر المباشرة

← العودة إلى الرئيسية

في المعمارية التقليدية، خدمة (أ) تستدعي خدمة (ب) مباشرة. في Event-Driven، (أ) تنشر حدثاً "حدث شيء ما" و(ب) تستمع وتتفاعل — دون أن تعرف (أ) عن (ب) أصلاً.

1. الفكرة الأساسية

# تقليدي: طلب مباشر — اقتران شديد (coupling) def order_created(order): email.send(order.customer) # (أ) تعرف (ب) مباشرة inventory.reduce(order.items) invoice.create(order) # Event-Driven: نشر حدث — فك اقتران كامل event_bus.publish("order.created", order) # مستمعون منفصلون يستجيبون للحدث event_bus.subscribe("order.created", email_handler) event_bus.subscribe("order.created", inventory_handler)
💡 الفائدة: أضف مستمعاً جديداً دون تعديل أي كود قديم. الخدمات مستقلة تماماً وتُطوَّر وتُنشر منفصلة.

2. الأنماط: Pub/Sub و Event Bus

  • Pub/Sub: ناشر + مشتركون عبر broker (Redis، RabbitMQ، Kafka)
  • Event Sourcing: تخزين كل الأحداث كسجل (قابل لإعادة البناء)
  • Event Bus محلي: داخل تطبيق واحد — بسيط وسريع

3. تنفيذ بسيط بـ Redis Pub/Sub

import redis r = redis.Redis() # الناشر (المُنتج) def publish_order(order_id, amount): r.publish("order.created", f"{{'order_id': {order_id}, 'amount': {amount}}}") # المشترك (المستهلك) — عملية منفصلة pubsub = r.pubsub() pubsub.subscribe("order.created") for message in pubsub.listen(): if message["type"] == "message": print("أحداث جديدة:", message["data"]) # أرسل إشعاراً، حدث المخزون، سجّل...

4. في أنظمة AI

الـ Event-Driven أساسي لأنظمة الوكلاء: وكيل ينشر حدث "اكتمل البحث"، ووكيل آخر يستمع ليكتب التقرير، وثالث يراجع. هذا هو جوهر أنظمة Multi-Agent غير المتزامنة.

⚠️ التحدي الأكبر: الترتيب وعدم اليقين. الحدث قد يصل متأخراً أو مكرراً. صمّم معالجات idempotent (تتحمل التكرار) وراقب تدفق الأحداث.
